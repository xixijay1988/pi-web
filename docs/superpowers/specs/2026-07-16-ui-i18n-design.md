# Pi Web English / Simplified Chinese UI Design

**Date:** 2026-07-16
**Status:** Foundation shipped; full UI migration in progress
**Scope:** All existing user-facing application UI

## 1. Objective

Add a global interface-language system supporting English (`en`) and Simplified Chinese (`zh-CN`). The first visit follows the browser language; an explicit user selection overrides browser detection and persists locally.

The feature translates fixed application UI only. It does not translate agent replies, historical messages, code, repository files, Markdown artifacts, model names, provider identifiers, API fields, role IDs, event types, or persisted Team Run data.

## 2. Product Decisions

- Supported locales: `en`, `zh-CN`.
- First visit: use `navigator.language` / `navigator.languages`.
- Any Chinese browser locale (`zh`, `zh-CN`, `zh-Hans`, and related variants) maps to `zh-CN`; all other locales map to `en`.
- User selection is stored under `pi-locale` in `localStorage` and takes precedence on later visits.
- Language switching is immediate and does not reload the page.
- Existing URLs, routes, APIs, session files, Team Run files, and `.team/**` artifacts do not change.
- User-facing technical terms are translated fully: Agent → 智能体, Skill → 技能, Model → 模型, Provider → 供应商, Team Run → 团队任务.
- Unknown server/runtime error details remain in their original language so diagnostic information is not lost.

## 3. Architecture

Use a small in-repo typed dictionary layer rather than introducing locale routes or a third-party i18n framework.

### Modules

```text
lib/i18n/
  locale.ts                 locale type, detection, normalization, storage key
  interpolate.ts            `{name}` variable replacement
  dictionaries/
    en/
      common.ts
      navigation.ts
      chat.ts
      team.ts
      settings.ts
      files.ts
      errors.ts
      index.ts
    zh-CN/
      common.ts
      navigation.ts
      chat.ts
      team.ts
      settings.ts
      files.ts
      errors.ts
      index.ts
  index.ts                  English key type + locale dictionary registry

components/
  LocaleProvider.tsx        current locale, persistence, document.lang
  LanguageSwitcher.tsx      shared top-bar/settings control

hooks/
  useI18n.ts                `t(key, variables?)`, locale, setLocale
```

The English dictionary is the source of truth. `TranslationKey` is derived from its keys. The Simplified Chinese dictionary must satisfy the same key set at compile time.

Keys are flat, domain-prefixed strings such as:

```ts
"common.cancel"
"chat.send"
"team.acceptance.rework"
"settings.models.title"
```

Flat keys keep lookup and type checking simple and avoid a recursive dictionary/type utility.

## 4. Runtime Data Flow

1. `LocaleProvider` initially exposes a hydration-safe English snapshot.
2. On the client, it reads `pi-locale`.
3. If no stored value exists, it normalizes the browser language.
4. It updates React subscribers and sets `<html lang="en">` or `<html lang="zh-CN">`.
5. `useI18n()` resolves the selected dictionary and returns translated strings.
6. `setLocale()` updates state, `<html lang>`, and `localStorage` immediately.

Storage access is best-effort. Private mode, blocked storage, or quota errors must not break the application; the selected locale remains active in memory for the current page.

A missing Chinese key falls back to English. Development builds emit a console warning containing the missing key; production remains quiet.

## 5. Translation API

```ts
const { locale, setLocale, t } = useI18n();

t("team.acceptance.failedCount", { count: failedChecks.length });
setLocale("zh-CN");
```

Interpolation replaces exact `{variable}` tokens. Values are converted to strings. The initial implementation does not add pluralization rules, rich-text translation nodes, date libraries, or locale routes.

Dates and numbers already rendered by the browser should use the active locale when calling `toLocaleString`, `toLocaleTimeString`, or `Intl.NumberFormat`.

## 6. Language Controls

### Top toolbar

Add a compact language button near the existing theme control. It displays `中文` while English is active and `English` while Chinese is active, indicating the action rather than repeating the current state. The accessible label describes the destination language.

On narrow/mobile layouts, the button may use a language icon plus a short label, but it must remain directly reachable without opening a settings modal.

### Settings area

The existing sidebar footer is the application's settings cluster (Models, Skills, Plugins, Roles). Add a language entry there showing the current interface language. Both controls use the same `LanguageSwitcher` behavior and provider state.

No new general settings subsystem is introduced solely for this feature.

## 7. Translation Scope

Translate every fixed user-facing string currently rendered by:

- application shell, top toolbar, product-mode navigation, sidebar, tabs
- session list, worktrees, file explorer, file viewer, download/preview states
- Chat input, controls, confirmations, branching, compaction, tool/model selectors
- Team creation, Goal Coach, Alignment Room/workspace, Timeline, acceptance and rework UI
- Models, Skills, Plugins, Roles, authentication, provider configuration modals
- empty states, loading states, tooltips, accessible labels, validation messages, confirmation dialogs
- client-generated success/error messages

Do not translate:

- assistant/user/tool message content
- session history content and exported session bodies
- source files, filenames, paths, commands, code blocks, URLs
- Team Run artifacts and model-generated plans/reports
- provider/model/package/skill identifiers and user-defined names
- server API contracts or persisted status/event values
- internal prompts and validation heuristics unless they are separately displayed as UI text

When an internal status must be displayed, map it to a translation key rather than changing the stored value.

## 8. Error Handling

- Translate fixed client context such as “Failed to load file”.
- Preserve unknown server error bodies and append them after translated context when useful.
- Never translate or rewrite stack traces, command output, model errors, provider errors, or filesystem paths.
- Missing translation keys return English text rather than the key itself.
- Invalid stored locale values are ignored and replaced by browser detection.

## 9. Migration Plan

Implementation is divided into independently verifiable batches, while the feature is considered complete only after all existing UI is covered.

1. Core locale modules, provider, hook, browser detection, persistence, top/footer controls.
2. App shell, navigation, sidebar, tabs, Chat, file explorer and file viewer.
3. Team mode, Alignment, Timeline, acceptance, rework and role configuration.
4. Models, Skills, Plugins, providers, authentication and remaining configuration dialogs.
5. Repository-wide user-visible string inventory, accessibility labels, confirmation dialogs and final parity sweep.

Each batch should be a focused commit and keep English behavior unchanged.

## 10. Testing

### Unit tests

- locale normalization and browser-language mapping
- stored user preference precedence
- invalid stored locale fallback
- interpolation with known and missing variables
- English and Simplified Chinese dictionary key parity
- missing-key English fallback

### Static validation

- TypeScript verifies dictionary key parity and valid translation-key usage.
- ESLint runs on touched paths.
- A repository string inventory identifies remaining user-visible hard-coded strings; explicit exclusions cover tests, prompts, API contracts, SVG data, code examples and non-UI content.

### UI smoke checks

Run in both locales:

- switch Chat / Team modes and reopen the application
- create/open a chat session and use primary Chat controls
- open files and preview common file states
- create/open a Team Run, Alignment workspace and acceptance flow
- open Models, Skills, Plugins and Roles dialogs
- verify mobile toolbar/sidebar language controls
- verify unknown API/model errors retain diagnostic details

Run existing tests, `node_modules/.bin/tsc --noEmit`, and targeted ESLint. Do not run `next build` during development.

## 11. Acceptance Criteria

- A new Chinese-browser user receives Simplified Chinese after client hydration.
- A non-Chinese-browser user receives English.
- The user can switch language from both the top toolbar and settings cluster.
- The explicit selection survives refresh and browser restart when storage is available.
- All existing fixed UI has English and Simplified Chinese translations.
- Switching locale does not mutate sessions, Team Runs, artifacts, messages, code, paths, model/provider values, or URLs.
- `<html lang>` matches the selected locale.
- Dictionary parity, locale selection, interpolation, TypeScript and lint checks pass.
- Unknown runtime/server errors remain diagnostically useful.

## 12. Non-Goals

- locale-prefixed URLs such as `/zh-CN/...`
- automatic translation of agent responses or generated artifacts
- per-conversation response-language settings
- additional languages beyond English and Simplified Chinese
- server-side locale negotiation or translated API response contracts
- pluralization framework, ICU MessageFormat, or translation-management service
